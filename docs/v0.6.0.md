# copper-cloud v0.6.0

Chat on shared canvases with @mention notifications, and a checklist (RSVP) shape that the REST
API reads and writes like the page does. Additive only: 0.5 clients keep working unchanged.

### Chat and mentions

- **Chat lives in the canvas.** Copper keeps a shared canvas's chat in the canvas document — a
  top-level `Y.Array` named `chat` of plain objects
  `{id, authorId, authorName, text, mentions, at, editedAt?, deleted?}`. The server relays,
  persists, compacts and reloads it like the rest of the document (sealed at rest under the
  canvas key); tests prove it survives room eviction, a server restart and snapshot
  compaction intact. Nothing on the server writes it.
- **`/read` shows the conversation.** `GET /v1/canvases/{id}/read` gains `chat`: the last 50
  messages, oldest first (deleted ones left out, text cut to 500 characters unless
  `full=true`), so agents can read the chat next to the board.
- **Mentions notify people.** `POST /v1/canvases/{id}/mentions`
  `{message_id, user_ids, excerpt}` — sent by Copper after a message that @mentions people —
  stores one mention per recipient who is a current member (never the sender), idempotent per
  message and recipient, and sends each new recipient a `canvas` event with kind `mention`.
  Response `{notified, skipped}`. Excerpts (≤ 200 characters) are sealed under the canvas
  key. 60 calls per minute per user; `429` beyond.
- **An inbox.** `GET /v1/mentions?unread=1&limit=n` lists your mentions on canvases you can
  still see, newest first (`{mentions: [{id, canvas: {id, name}, from: {id, display_name,
  email}, message_id, excerpt, created_at, read_at}], unread}`; limit ≤ 100).
  `POST /v1/mentions/read` with `{ids}` or `{canvas_id}` marks them read and sends you a
  `canvas` event with kind `mention_read` so your other devices clear their badges.
- **Version gate.** `/v1/info` reports `0.6.0`; Copper enables mention notifications from this
  version on. Against an older server, chat still works (it is in the document) but mentions
  are in-canvas only.
- New counters `canvas_mentions_total` and `canvas_mentions_rate_limited_total`.

### Checklist (RSVP) shape

- **A new shape type, `checklist`.** A card with a `title`, 1–4 `columns` (default
  `["Yes","No"]`; one column is a plain to-do list) and up to 60 `rows` (`[{id, label}]`).
  Each row has at most one pick. A pick is stored under its row's own key —
  `pick:<rowId>` → `{col, by, byId, at}` — so people picking different rows at the same
  moment never overwrite each other; `columns` and `rows` are whole values (last writer wins).
  Rooms relay and persist it like any other shape.
- **REST parity with the page.** `POST /v1/canvases/{id}/ops` `add`/`update` accept `title`,
  `columns`, `rows` (`"Ann"` or `{label, id?}`) and `picks` (`{"Ann": "Yes", "r3": null}`;
  a row by id or label, a column in any case, `true` for the first, `null`/`false`/`""` to
  clear) with the page's prop names, validation and limits (≤ 4 columns × 40 characters,
  ≤ 60 rows × 200 characters). Picks are attributed to `as`, else the caller. `GET /read`
  returns `title`, `columns`, `rows: [{id, label, pick, by?, at?}]` and an ordered
  `tally: {column: count}`. Details in `docs/canvas-protocol.md`.
- **Older clients** (Copper ≤ 1.0.20261006.28, copper-cloud ≤ 0.5.0) do not show or read a
  checklist but keep it intact.

The canvas test suite reads `COPPER_CLOUD_TEST_CANVAS_DATABASE_URL` (default unchanged), so
parallel checkouts can each use their own database.

Migration `0103_canvas_mentions` adds the `canvas_mentions` table. Upgrade in place with the
release tarball's `install.sh` (keeps config, keys, certificate and link codes; applies the
migration).
