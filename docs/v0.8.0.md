# copper-cloud v0.8.0

People can delete their own synced browsing history from the cloud. Additive only: 0.7 clients
keep working unchanged.

- **The server never looks inside history to delete it.** Selecting rows is done only by
  metadata the server already stores in the clear — `seq`, `visited_at`, the pushing device.
  No delete path opens a payload or even unwraps the user's data key. Choosing individual
  entries ("forget this site", "remove these visits") is the user's call and happens in Copper:
  it pulls its history (`GET /v1/sync/history` returns every row's `seq`), filters locally and
  sends the seqs it picked.
- **`DELETE /v1/sync/history`.** Same gate and session as the other sync routes; scoped to the
  caller's own rows. Exactly one of:
  - body `{"seqs": [<seq>, …]}` (up to 5000) — deletes exactly those rows where they are the
    caller's; other users' or unknown seqs are silently ignored; `[]` deletes nothing;
  - query `since` (RFC 3339, inclusive), `until` (exclusive) and/or `device` (a device id),
    combinable — deletes the rows matching all of them;
  - nothing — deletes all of the caller's history.

  Answers `200 {"deleted": n}`. One SQL statement; sequence numbers are never reused, so a
  device's stored pull cursor stays valid (it just sees fewer rows).
- **Strict input.** More than 5000 seqs, seqs together with query filters, a body that is not
  exactly `{"seqs": [<integer>, …]}`, an unparsable or repeated parameter, `since` not before
  `until`, or any unknown parameter (`host`, `url`, …) is a `400 bad_request`; a body over
  256 KiB is a `413` — a malformed request never turns into "delete everything".
- **Rate limit.** 20 deletes per minute per user (bursts of 20), `429 rate_limited` beyond.
- **`history_deleted` event.** After every delete (even one that removed nothing) the user's
  streams get
  `{"type":"history_deleted","deleted","since","until","device","seqs"?,"device_id"}` — the
  metadata filter for a filter delete (so other devices can apply it locally), or `seqs` = how
  many distinct seqs were asked for. Never urls, hosts or other content. Clients may ignore it.
- **`GET /v1/info` → `features`.** A new array, `["history_delete"]`, so a Copper can show the
  control only on servers that support it. It only ever grows.
- **CLI.** `copper-cloud admin history delete --user <email|uuid> [--since T] [--until T]
  [--device ID] [--dry-run]` — wholesale, metadata only (no content filters); prints only the
  count (`--dry-run` only counts). Coppers are not notified of CLI deletes; they see fewer rows
  on their next pull.
- **Observability.** Counters `history_deleted` and `history_delete_rate_limited_total`; one
  `history deleted` log line per delete with counts and which filters were used only.

No migration. Upgrade in place with the release tarball's `install.sh`.

See [api.md](api.md#delete-v1synchistory) and [operations.md](operations.md#synced-history).
