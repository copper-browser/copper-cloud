# copper-cloud v0.9.0

Company single sign-on, one-link onboarding, agent pairing and hybrid TLS. Additive only:
0.8 clients keep working unchanged.

- **Single sign-on.** Google Workspace, or any OpenID Connect provider found by issuer
  discovery, set up in the portal or with `copper-cloud admin sso set-google|set-oidc`.
  - Copper uses the native-app flow (loopback redirect + PKCE S256). The server keeps the
    client secret, encrypted at rest, and does the code exchange.
  - It checks the ID token's `iss`, `aud`, `exp`, `email_verified` and email domain. For
    Google, the Workspace `hd` must also be allowed.
  - Accounts are found by linked identity, then by email (linking it), then created with no
    password unless `auto_create` is off.
  - The device gets a session and gate key exactly as with a pairing code.
  - Routes: `GET /v1/auth/sso` (public provider list) and `POST /v1/auth/sso/{provider_id}`.
    Both are ungated; sign-in is auth-rate-limited.
  - Setup walkthrough: [sso.md](sso.md).
- **Password sign-in policy.** `password_signin = false` (portal, or
  `admin sso password-signin off`) refuses password signup/login for people with
  `403 password_signin_disabled`. Admins are unaffected. Accounts created by SSO have no
  password; password login for them answers `401 sso_only`.
- **`/start` onboarding page.** Server-rendered with no external assets:
  1. install Copper (Mac zip / Homebrew cask, Linux one-liner);
  2. **Open in Copper** (`copper://cloud/join?code=<join link>`, plus the link as copyable
     text);
  3. **Continue with Google**.

  It shows a polite "not set up yet" page until a provider is enabled. The join link
  (`copper-cloud://HOST:PORT/#sso=google[&fp=…]`) holds no secret: `copper-cloud link-code
  --sso` prints it. The page's name comes from the new `instance_name` setting.
- **Agent integrations.** An admin mints a `cai_…` key (portal or
  `copper-cloud admin integration create`). A trusted service then calls
  `POST /v1/agents/pair` with it to get a single-use pairing code **bound to a device id**
  for any user in the allowed domains; it can create the account if allowed.
  - Re-pairing a device revokes its previous session and gate key.
  - Rotate and revoke cut the key off at once; revoke also signs out its agent devices.
  - `POST /v1/auth/pair` honours the bound device id.
- **Admin API.** `GET/PATCH /admin/api/sso`, `PUT/DELETE /admin/api/sso/providers/{id}`,
  `POST …/{id}/test` (credentials probe), `GET/POST /admin/api/integrations`,
  `POST …/{id}/rotate`, `DELETE …/{id}`, `GET …/{id}/devices`, and `instance_name` in
  `settings` ([admin-api.md](admin-api.md#single-sign-on-090-older-servers-answer-404)).
- **Hybrid TLS.** `tls.mode = "acme"` + `tls.fallback_self_signed = true` serves the Let's
  Encrypt certificate to clients asking for `tls.domain`. Everyone else (raw IP, no SNI) gets
  the existing self-signed certificate, which is never regenerated. Pinned Coppers keep working
  while new onboarding (SSO join link, `/start`, agent links) uses the domain without `fp`.
  See [operations.md](operations.md#adding-a-domain-to-an-existing-self-signed-instance).
- **`GET /v1/info` → `features`** gains `"sso"` and `"agent_pairing"`.
- **Doctor** reports the providers (secret stored, domains), the `/start` URL and join link,
  the integrations, and the hybrid TLS links.

Migrations `0012_sso` (providers, identities, nullable `users.password_hash`, the
`password_signin` setting) and `0013_agent_integrations` (integrations, agent device flag,
device-bound pairing codes, access keys remembering their device). Both are applied at start.
Upgrade in place with the release tarball's `install.sh`.
